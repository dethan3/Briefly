# Output Contract

Use this exact section order in `summaries/<basename>.md`. Adapt only where the source type requires a documented downgrade.

## Required structure

```md
# <标题>

## 核心议题
用 1-2 句定义这期内容试图回答的问题。

## 论证主线
按逻辑重组主要论证，不按字幕时间顺序复述。

## 立场对垒
多人内容时，列出关键人物、观点冲突点、分歧类型、各自隐含前提。

## 硬核数据
列出所有出现的百分比、金额、估值、增长率、时间区间、宏观指标及其上下文。

## GSD 行动点
给独立开发者或小团队的 3-5 个具体机会、产品路径或技术路径。

## 金句库
保留 3 条最有洞察力的原话，尽量附带 speaker 和时间范围。

## 不确定项
标出预测、观点、未经验证的断言、归因不稳的内容。

## 一句话结论
用一句话说明这期最值得记住的判断。
```

## Section rules

### 核心议题

- 写成问题定义，不是泛泛摘要。
- 避免“本期主要讨论了”这种低信息句式。

### 论证主线

- 聚合零散发言，恢复成 4-8 段有因果关系的论证。
- 去掉广告、重复寒暄和无关玩笑。
- 明确结论依赖的关键前提。

### 立场对垒

- 只在多人内容中使用。
- 分清楚分歧属于事实判断、因果解释还是策略建议。
- 无法确认 speaker 时，改写成 `支持方观点`、`反对方观点`、`主持人追问`。

### 硬核数据

- 尽量穷尽数字信号，不只列最醒目的几个。
- 每条数据都给一句上下文，说明数字是事实、预测还是引用他人观点。
- 没有明确数字时，写 `未出现可验证的硬数字`，不要编造表格。

### GSD 行动点

- 必须具体到独立开发者或小团队可执行。
- 优先写可做的产品、工作流、工具链、研究跟踪线。
- 不要写“持续关注”“多学习”这类空话。

### 金句库

- 引用要短而硬，不要为了文采而改写。
- 如果字幕噪音较重，可以做轻量清洗，但不能改变意思。
- 引用必须能在 `segments.json` 中追溯。

### 不确定项

- 明确哪些是事实，哪些是预测，哪些只是嘉宾判断。
- 标记未被验证但影响结论的断言。
- 标记 speaker 归因、翻译、ASR 质量带来的风险。

## Single-speaker downgrade

如果源材料是单人演讲或单人访谈，将 `立场对垒` 替换为：

```md
## 关键判断与隐含假设
列出主讲人的核心判断，以及这些判断成立所依赖的前提。
```
